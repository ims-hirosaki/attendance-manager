## 2. ブランチ・デプロイ・CI【確定】

| ワークフロー | トリガー | 動作 |
|---|---|---|
| `deploy.yml` | `main` への push | FTP（XSERVER）で**本番**の `wp-content/plugins/attendance-manager/` へ反映 |
| `staging-deploy.yml` | `staging` への push | FTP でステージング環境へ反映 |
| `personal-deploy.yml` | `feature/shiroto*` ブランチへの push | 個人テスト環境へ反映 |
| `validate.yml` | すべての push / PR | ① マージコンフリクトマーカー検出 ② `find . -name '*.php' | xargs -n1 php -l`（PHP構文）③ `node --check assets/js/admin.js` |

- FTP の接続情報は GitHub Secrets（本番/ステージング/個人で別）。`dangerous-clean-slate: false` のため、**リポジトリで削除したファイルはサーバーから自動では消えない**。
- 本番（`main`）への push は**即時デプロイ**。レビュー前提のブランチ運用（staging → main の PR マージ）がコミット履歴から読み取れる。【推定】
- **注意**: リポジトリ全体が FTP で転送されるため、`docs/`、`.codex-build/`、拘束時間のUPSERT用SQL（`拘束時間管理表_2026-07-01_upsert.sql`、実データ1,714行）、`CLAUDE.md` 等もデプロイ先に置かれ得る。（除外設定は無い。デプロイ先ディレクトリが Web 公開領域かは未確認）【要確認：ISS-08】

## 5. 処理フロー（コード上の呼び出し関係）

### 5.1 長距離画面の表示
```
render_chokyo_page
  ├ AM_DB::get_employees_by_category('chokyo')          ← BR-01
  ├ AM_DB::get_emp_info_by_id / get_crew_codes_for_period
  ├ AM_Compute_Chokyo::get_monthly_rows                 ← パス1〜3
  │    ├ AM_DB::get_chokyo_saved_kintai / get_active_rules_by_affiliation
  │    ├ AM_DB::get_paidleave_consumed_dates / get_chokyo_carryover
  │    ├ apply_hosei → 有給反映 → 自動補正 → apply_auto_kintai → mark_unmatched_houtei_work
  ├ AM_Compute_Chokyo::get_weekly_summary
  │    └ _build_weekly_static ─(月またぎ週)→ AM_DB::save_chokyo_carryover   ★書き込み副作用
  └ AM_Compute_Chokyo::get_monthly_summary
  → include templates/chokyo-page.php（_weekly-table / _monthly-summary を include）
```
> ★ **画面表示（GET）で DB 書き込みが起きる**（翌月繰越の UPSERT）。キャッシュ層や読み取り専用DBを導入する場合に要注意。

### 5.2 保存
```
admin.js #am-btn-save → AM_Ajax::chokyo_kintai_save
  → トランザクション内で日付ごとに UPDATE/INSERT → {saved}
  → admin.js が API-02/03/04 を連続呼出して部分更新（フラグ操作時は location.reload）
```

### 5.3 集計一覧
```
admin.js #am-sl-load → AM_Ajax::summary_list_get
  → 長距離社員ごとに get_monthly_rows → get_weekly_summary → get_monthly_summary
  → 地場・事務社員ごとに同様 → 行整形（バッジ付与）
```
**社員数×月次計算（外部DBクエリ多数）を1リクエストで実行**。社員数が増えると遅くなる（性能上の懸念）。

## 7. セキュリティ【確定】

| 項目 | 状況 |
|---|---|
| 認証・権限 | すべての AJAX/admin-post/ページで `current_user_can()`。表示は access、保存は edit、設定は manage |
| CSRF | AJAX は nonce `am_nonce`。admin-post は個別 nonce（`am_summary_csv_export` / `am_kousoku_csv_import` / `am_kousoku_csv_template`） |
| SQL | `$wpdb->prepare()` を基本使用。動的 `IN` はプレースホルダー生成。一部の `SHOW TABLES LIKE '{$t}'` は内部生成のテーブル名を連結（外部入力なし） |
| XSS | テンプレートは `esc_html` / `esc_attr`、JS は textで挿入。ただし休日ルール一覧の再描画（`hmReloadTable`）は `week_numbers` / `affiliation_id` 等を HTML 属性へ未エスケープで連結しており、種別管理の行も `data-name` の引用符をエスケープしていない（入力できるのは設定権限者のみで低リスク。ISS-07） |
| ファイルアップロード | CSV は拡張子・サイズ・`is_uploaded_file`・行数・UTF-8・各値の厳格な検証。全体トランザクション |
| 権限昇格 | `migrate_existing_tables` は `manage_custom_plugin_settings` 保持者の admin_init のみ |
| 機密 | FTP 資格情報は GitHub Secrets。ソース内に資格情報は無い |

## 8. 性能に関する留意点
- **毎回、元データから全日再計算**する設計。1リクエストあたり、社員1名で十数回の SELECT（kousoku、tenrec、MAT、保存編集、休日、有給、繰越…）。
- tenrec は月の全日の `entries`（JSON）を取得して PHP 側で社員名を探す。
- 集計一覧・集計CSVは**全社員分**をループ（社員数に比例して増加）。
- `admin_init` のマイグレーションは、権限保持者の**管理画面表示のたびに** `SHOW TABLES / SHOW COLUMNS / UPDATE ... JOIN` を実行する（冪等だが毎回走る）。

## 10. 検証方法（コードを変えたとき）

自動テストは無いが、**純粋関数はスタブで単体実行できる**。本書の数値例はこの方法で検証した:

class AM_DB {                                    // 必要な最小スタブ
  static function get_hosei_start_month(){ return '2026-01'; }
  static function save_chokyo_carryover($k,$m,$d){ /* 記録 */ }
  static function save_jiba_carryover($k,$m,$d){}
}
require 'includes/class-am-compute-chokyo.php';
// $rows = [ ['date'=>'2026-09-01','has_data'=>true,'labor_min'=>480,'hosei_min'=>10,
//            'kousoku_min'=>540,'drive_min'=>0,'cargo_min'=>0,'midnight_min'=>0,
//            'overtime_min'=>0,'start_time'=>'08:00','end_time'=>'17:00'], ... ];
// $rows = AM_Compute_Chokyo::apply_hosei($rows, '2026-09');
// $w = AM_Compute_Chokyo::_build_weekly_static(1,'2026-09',$rows,'2026-09-01','2026-09-30',null,'chokyo');

- `apply_auto_kintai`・`mark_unmatched_houtei_work`・`format_min` も `$wpdb` 無しで動く（必要な行キーは `date, is_sun, is_shitei_holiday, has_data, default_kintai, furikae_label, is_manual`）。

### 変更時の回帰確認観点
1. 長距離・地場それぞれで、通常月／月またぎ週のある月／日曜出勤あり／所定休日出勤あり。
2. 補正時間: 適用開始月の前後。地場の長距離フラグ ON/OFF。
3. 乗務員コード複数保有（月中変更・同日重複）。
4. 前月→翌月の繰越連続性（前月を再表示しない場合の差）。
5. 集計一覧と各社員画面の数値一致、集計CSVとの突合（ISS-02, ISS-04）。
6. 権限別（access のみ／edit あり／manage あり）の表示と保存。
