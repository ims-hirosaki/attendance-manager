# 社内ツール共通 API 発行ルール

Excel（Power Query）などの外部ツールからデータを取得する REST API を、各 WordPress プラグインで発行するときの共通ルール。
勤怠管理プラグイン（`includes/class-am-rest-api.php`）の実装を基準にしている。

## 1. 基本方針

- REST API は WordPress 標準の `register_rest_route` で作る。`admin-ajax.php` / `admin_post` は管理画面用で、外部ツールからは使わない。
- 取得専用（`GET`）にする。データの更新・削除は API で行わない。
- 重い処理は 1 リクエストにまとめすぎない（§6）。
- 1 つのプラグインで API を追加するときは、専用クラス（例: `class-xx-rest-api.php`）にまとめ、プラグイン本体から `init()` を呼ぶ。

## 2. URL の決め方

```
/wp-json/{プラグイン識別子}/v1/{リソース名}
```

| 項目 | ルール | 例 |
|---|---|---|
| namespace | `{プラグイン識別子}/v1`（ハイフン区切り、バージョン付き） | `attendance-manager/v1` |
| リソース名 | 小文字・ハイフン区切り。名詞にする | `employees`、`timesheet`、`timesheet-all` |
| パラメータ名 | 小文字・スネークケース | `employee_code`、`year_month` |
| 対象月 | `YYYY-MM` 形式で受け取り、正規表現で検証する | `2026-09` |

- 破壊的な変更（項目名の変更・削除）をするときは、`v2` を新設して `v1` を残す。項目の追加は `v1` のままでよい。
- 一括取得など試験的なものは、本番運用が決まるまでドキュメントに「試験的」と明記する。

## 3. 認証・権限

### 認証方式

- **WordPress のアプリケーションパスワード（Basic 認証）** を使う。独自のトークン方式は作らない。
- HTTPS 必須（アプリケーションパスワードは HTTPS でないと使えない設定が標準）。

### 専用ロール「API取得」

- 全ツール共通で、ロール「**API取得**」（スラッグ `api_reader`）を使う。ツールごとにロールを増やさない。
- ロールは各プラグインの `init` で確認し、**無ければ作成、あれば作り直さずに自プラグイン用のケイパビリティだけ追加**する。

```php
public static function ensure_role() {
    $role = get_role( 'api_reader' );
    if ( ! $role ) {
        add_role( 'api_reader', 'API取得', [ 'read' => true ] );
        $role = get_role( 'api_reader' );
    }
    if ( $role && ! $role->has_cap( 'xx_export_data' ) ) {
        $role->add_cap( 'xx_export_data' );
    }
}
```

- ケイパビリティはプラグインごとに分ける。命名は `{プレフィックス}_export_data`（例: `am_export_data`）。
  - 同じロールを付けても、プラグインごとに権限が分かれるので、Excel 担当者に見せるデータを制御できる。
- `permission_callback` は必ず指定する。未ログインは **401**、権限不足は **403** を返す。
- ロール名の付け替えや削除は、既存ユーザーに影響するため、事前に周知する。

### ユーザー運用

- Excel 担当者ごとに WordPress ユーザーを作る（共有アカウントにしない）。
- WordPress のユーザー作成にはメールアドレスが必須（実在しなくてもよいが、重複は不可）。実在しないアドレスを使う場合は自社ドメイン内にする。
- アプリケーションパスワードは、そのユーザーのプロフィール画面で発行する。発行直後の 1 回しか表示されないので、その場で控える。
- 退職・異動時は、そのユーザーのアプリケーションパスワードを失効する（またはユーザーを削除する）。
- パスワードをブック・メール・チャットに書かない。Power Query の認証情報として設定する。

## 4. エンドポイント設計

### 推奨の 2 本立て

| 種類 | 役割 | 例 |
|---|---|---|
| マスタ一覧（軽量） | 選択肢・対象一覧を返す | `GET /employees` |
| 詳細データ（1 件単位） | 1 人 × 1 か月など、小さい単位で返す | `GET /timesheet?employee_code=&year_month=` |

- まず「1 件単位」で作る。Excel 側から「一覧 → 1 件ずつ呼ぶ」で全件を組み立てられる。
- 一括取得が必要な場合のみ、別 URL（例: `timesheet-all`）で追加する。

### 入力パラメータ

- `args` で型・必須・正規表現・列挙値を定義して、WordPress 側で検証させる。
- 受け取る識別子は、利用者が分かる値（社員コードなど）にする。内部 ID への変換は API 内部で行う。
- 対象が見つからない場合は **404**、入力が不正な場合は **400**、データの不整合（内部 ID が特定できないなど）は **422** を返す。

## 5. レスポンス形式

- 形式は **JSON**。Power Query で扱いやすいよう、トップレベルは配列かオブジェクトにする。
- 項目名は英語のスネークケース（`employee_code`、`labor_min`）。表示用の日本語ラベルは API に含めず、Excel 側で付ける。
- **計算後の値を返す**。調整・補正がある項目は、合算後の値とは別に調整分だけの項目も返す（例: `labor_min` と `hosei_min`）。
- 時間は **分単位の整数**（`*_min`）を基本とし、表示用に `H:MM` 文字列（`*_min_hm`）を併記する。計算には `*_min` を使う。
- 一括取得では、次の項目を付ける。
  - `total_employees`（対象件数）、`returned`（返した件数）、`offset`
  - `elapsed_sec`（かかった秒数）
  - `errors`（失敗した対象の識別子と理由。空配列なら全件成功）
- 1 件の失敗で全体を止めない。失敗は `errors` に積んで続行する。

## 6. 重い処理の扱い

1. **1 件単位の API を基本にする**（1 リクエストあたりの処理を小さくする）。
2. 一括取得では `offset` / `limit` で分割取得できるようにする。
3. `set_time_limit()` と `wp_raise_memory_limit()` を設定する（サーバー側の制限が優先される場合がある）。
4. 試験段階では `elapsed_sec` を返して、実際の重さを測れるようにする。
5. 全件を 1 リクエストで返す API は、試験で重さを確認してから公開する。

## 7. キャッシュ

- 確定済みのデータ（前月以前など）のみ、**transient で 1 日キャッシュ**する。当月・未来月はキャッシュしない。
- キャッシュキーには「バージョン番号（オプション値）」を含める。データの保存・設定変更・CSV 取込などの書き込み処理で、バージョン番号を更新して全キャッシュを無効化する。

```php
// 書き込み処理の成功時
AM_REST_API::invalidate_cache();
```

- `refresh=1` で強制再計算できるようにする。
- 外部テーブル（他システムが更新するデータ）は更新を検知できない。データ修正の直後に最新を見たい場合は、`refresh=1` を使う。

## 8. 動作確認

### curl での確認

```bash
curl -u 'USER:APP_PASSWORD' 'https://ドメイン/wp-json/{namespace}/v1/employees'
```

- 200 → 正常。
- 401（認証できない）→ XSERVER で Authorization ヘッダーが PHP に届いていない可能性がある。`.htaccess` に次を追記する。

```
RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]
```

- 404 / WordPress のエラーページ → URL（サブディレクトリ設置の場合は `/サブディレクトリ/wp-json/...`）、およびパーマリンク設定（「基本」だと `?rest_route=/...` の形になる）を確認する。
- ログインしていないブラウザで URL を開いて、`{"code":"..._forbidden",...}` が返れば、API 自体は動いている（権限エラーが正しく返っている）。

### 公開前のチェックリスト

- [ ] `permission_callback` を指定した（未ログイン 401 / 権限不足 403）
- [ ] 入力パラメータを `args` で検証している
- [ ] ロールは「API取得」を共有し、プラグイン専用のケイパビリティを追加している
- [ ] 計算後の値を返し、調整分は別項目で返している
- [ ] 重い処理は 1 件単位、または `offset` / `limit` で分割できる
- [ ] キャッシュを使う場合、書き込み処理で無効化している
- [ ] 当月・未来月はキャッシュしていない
- [ ] ステージングで curl 確認（200 / 401 / 403 / 404）をした
- [ ] Power Query から実際に読み込めた
- [ ] 本ドキュメントの「利用中の API 一覧」に追記した

## 9. Power Query からの接続（要点）

1. データ → データの取得 → その他のデータソースから → **Web から**
2. URL を入力 → 認証は **「基本」**、ユーザー名とアプリケーションパスワードを設定（適用先はサイトのルート URL）
3. JSON の「List」→「テーブルへ」→ 列を展開 → 閉じて読み込む
4. パラメータ（社員コード・対象月など）を切り替える場合は、セルから値を渡す関数クエリにする（`Web.Contents` の `Query = [ ... ]` を使う）
